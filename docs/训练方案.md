## 2. 模型选型

### 2.1 候选对比

| 模型 | 参数量 | 中文能力 | License | 生态/工具链 | 备注 |
|---|---|---|---|---|---|
| **Qwen2.5-7B / -Instruct** | 7.6B | 强 | Apache-2.0 | 极好（transformers/trl 一等支持） | **推荐** |
| Llama-3.1-8B | 8B | 中 | Llama 3.1 社区许可 | 好 | 英文工业场景可考虑 |
| Mistral-7B-v0.3 | 7.3B | 弱 | Apache-2.0 | 好 | 中文场景不推荐 |
| Qwen2.5-14B | 14.7B | 强 | Apache-2.0 | 好 | **5090 32GB 可跑 LoRA**，M2 可升级 |

### 2.2 推荐与理由

- **默认推荐 Qwen2.5-7B-Instruct**：Mining-Engineering 为中文领域问答（含 CoT 推理），Instruct 版中文指令跟随与格式遵循能力更强；TRL 对其 chat template 原生支持；Apache-2.0 无商用障碍。
- **5090（32GB）显存红利**：7B LoRA 训练仅需 ~16GB，32GB 下 batch 可翻倍、seq 可加长，甚至可直接升级 **Qwen2.5-14B LoRA**（M2 对比实验）。
- 若后续工业任务是**纯生成式/格式学习**（如结构化抽取），可改用 **Qwen2.5-7B（base）**。

### 2.3 基线对照

所有实验必须同时评测**未微调基座**（zero-shot），作为效果增量基准（见 §8）。

## 3. 数据方案（已定案：Mining-Engineering 系列）

### 3.1 数据来源（合肥工业大学大创项目，中文，MIT）

| 数据集 | 规模 | 用途 |
|---|---|---|
| **`acnul/Mining-Engineering-SFT`** | **5,287 条** train | 正式训练（主） |
| `acnul/Mining-Engineering-SFT-CoT` | 5,287 条 train | **可选对比**：response 以 `<think>` CoT 开头（DeepSeek R1 两阶段蒸馏 + 事实对齐） |
| `acnul/Mining-Engineering-Eval` | **301 条** | 官方评测集 |
| `acnul/Mining-Engineering-Probe` | 50 条 | 快速验证集（调参期用） |

### 3.2 字段与内容

- 字段：`prompt`（指令/问题）、`response`（标准回答）、`source`（知识来源分类）
- **六大模块**（`source` 字段，支持分模块能力分析）：law 法律法规 / specifications 工程规范 / concept 专业术语 / safety 安全事故案例 / forum 行业实践经验 / synthesis 领域综合知识
- 模板化：`问：{prompt}\n答：{response}`（`loader.py::format_sample`），训练时保留 `source` 列用于分模块分析。

### 3.3 数据划分

- **直接用官方划分**：训练 5,287（不切分） + Eval 301 + Probe 50——三方独立、可复现。
- CoT 版为同源数据，仅用于对比实验（不混入主训练集）。

### 3.4 数据质量检查（训练前必做）

- [ ] 长度分布统计（P95 分位决定 `max_seq_length`；CoT 版 response 更长，需单独统计）
- [ ] 六模块样本量分布核对（`source` 计数）
- [ ] 空样本/坏样本剔除（空 prompt 或空 response）
- [ ] 抽查 response 质量（事实正确性、是否含 `<think>` 标签残片）
- [ ] PII/敏感信息抽查

## 4. 微调方法：LoRA（5090 下不用 QLoRA）

### 4.1 参数基线

| 参数 | 值 | 说明 |
|---|---|---|
| `lora_r` | 8（对比实验可 16） | 5 千条规模 r=8 起步合理 |
| `lora_alpha` | 16（= 2×r） | 经验比例 |
| `lora_dropout` | 0.05 | 防过拟合 |
| `lora_target_modules` | q,k,v,o,gate,up,down 全量 | 比只打 qkv 效果好，Qwen2.5 架构适用 |

### 4.2 为什么 5090 上直接 LoRA、不用 QLoRA（重要）

- **显存够**：7B LoRA bf16 约 16GB < 32GB，QLoRA 的省显存收益无意义；
- **Blackwell 兼容性**：bitsandbytes 4bit NF4 在 sm_120 上存在已知性能/能效惩罚（[bitsandbytes issue #1851](https://github.com/bitsandbytes-foundation/bitsandbytes/issues/1851)），且依赖版本敏感（需 ≥0.45 且 CUDA 12.9 支持仍在跟进中，[issue #1642](https://github.com/bitsandbytes-foundation/bitsandbytes/issues/1642)）；
- **速度**：LoRA bf16 比 4bit 量化训练快约 30~50%，且无量化误差。
- 结论：**M1 一律 LoRA bf16；QLoRA 仅作为未来 14B/全参时的备选**。

### 4.3 对比实验矩阵（M1 含 L1，其余 M2）

| 实验 | 数据 | r | CoT | 目的 |
|---|---|---|---|---|
| baseline | - | - | - | 未微调基座，效果增量基准 |
| **L1（M1 主实验）** | SFT | 8 | 否 | 跑通流程 + 主指标 |
| L2 | SFT | 16 | 否 | LoRA 容量对比 |
| C1 | SFT-CoT | 8 | 是 | **CoT 蒸馏数据效果对比**（重点） |
| Q1（可选） | SFT | 8 | 否 | 14B LoRA 可行性（M2） |

## 5. 训练超参基线（5090 优化版）

### 5.1 数值与理由

| 参数 | 值 | 理由 |
|---|---|---|
| `per_device_train_batch_size` | **4** | 32GB 显存充裕，比 24GB 卡的 2 翻倍 |
| `gradient_accumulation_steps` | **4** | 全局 batch = 4×4 = 16（不变，收敛性一致） |
| `learning_rate` | 2.0e-4 | LoRA 常用区间 1e-4 ~ 3e-4 的中值 |
| `lr_scheduler_type` | cosine | 收敛稳，配 warmup |
| `warmup_ratio` | 0.03 | 常用 3% |
| `num_train_epochs` | 3.0 | 5 千条规模 2~5 合理，3 为起点 |
| `max_seq_length` | 2048 | 矿建问答 + CoT 回答较长；按 P95 复核 |
| `bf16` | true | Blackwell 原生支持，5090 强项 |
| `gradient_checkpointing` | true | 继续开：显存换 batch 4 的空间，且与 `torch.compile` 可共存 |
| `weight_decay` | 0.01 | 常规正则 |
| `seed` | 42 | 可复现 |
| `logging_steps` / `save_steps` | 10 / 500 | 日志密集、checkpoint 稀疏 |

### 5.2 5090 加速开关（M1 落地，需 sft.py 接线）

| 开关 | 推荐 | 说明 |
|---|---|---|
| `torch.compile` | **开**（`mode="default"`） | 7B 训练可提速 10~30%，TRL SFTConfig 原生支持；首次编译有 ~1-2 分钟预热 |
| `attn_implementation` | **`sdpa`**（PyTorch 2.7+ 内置） | **FlashAttention-2 不支持 sm_120**（[参考](https://github.com/lllyasviel/FramePack/issues/327)）；SDPA 是 5090 上最稳的注意力实现；追求极致可装 FA3（源码编译，M2 再议） |
| `optim` | `adamw_torch_fused` | 融合优化器，省显存+提速，比 paged_adamw 更适配 Blackwell |
| `dataloader_num_workers` | 4 | 数据加载不拖 GPU |
| `use_reentrant` | false（若升级 transformers 后默认） | gradient checkpointing 新实现，更稳更快 |

### 5.3 优化方向（M2）

- 早停：观察 Eval 集指标（Probe 快速验证）。
- 学习率分段：先 2e-4 再降 5e-5（anneal）。
- 升级 **14B LoRA**（5090 32GB 可跑）：若 7B 效果不达预期，先升模型再考虑全参/RL。

## 6. 算力与时间预算（RTX 5090）

### 6.1 环境要求（Blackwell 特有，必读）

| 项 | 要求 | 原因 |
|---|---|---|
| GPU | RTX 5090（32GB，sm_120） | 已定案 |
| **PyTorch** | **≥ 2.7**（官方构建开始支持 sm_120） | 2.6 及更早报 "no kernel image available"（[参考](https://stackoverflow.com/questions/79833972/pytorch-not-recognizing-rtx-5090-sm-120-on-windows-11-cuda-error-no-kernel)） |
| **CUDA** | **≥ 12.8**（建议 12.8/12.9） | Blackwell 需要 |
| 操作系统 | **Windows 原生或 WSL2** | 训练建议 WSL2（Linux 栈更稳）；Windows 原生需严格按 2.7+ 安装 |
| FlashAttention-2 | **不要装/不要开** | sm_120 不支持；用 SDPA |
| bitsandbytes | 本方案不需要（不用 QLoRA） | 若未来 QLoRA 需 ≥0.45 且关注 CUDA 12.9 支持状态 |

### 6.2 显存参考（5090 32GB）

| 方案 | 显存需求 | 结论 |
|---|---|---|
| **LoRA 7B（推荐）** | ~16GB | ✅ 余量充足，可开 batch 4 / seq 4096 |
| LoRA 14B（M2 升级） | ~28-30GB | ⚠️ 可跑但紧，batch 2 + checkpointing |
| QLoRA 7B | ~10GB | 不需要（见 §4.2） |
| 全参微调 7B | >60GB | ❌ 单卡不可行 |

### 6.3 时间估算（5090）

- 训练集 5,287 条 × 平均 ~500 token ≈ 2.6×10⁶ token/epoch。
- 5090 bf16 稠密算力约 105 TFLOPS（比 4090 高 ~27%），配 `torch.compile` + batch 4，有效吞吐约 **2000~3500 tokens/s**。
- **单 epoch 约 15~25 分钟；L1 主实验 3 epoch 约 1 小时；全套对比（L1+L2+C1）半天内完成**。
- 评测 301 条 × 生成 ~200 token：HF 原生 generate 约 10~20 分钟；接入 vLLM 后可压到分钟级（M1 可选，见 §8.4）。
- **建议先跑 Probe/512 条冒烟校准吞吐**，再排正式训练。

### 6.4 多卡（M1 不需要）

- 5090 单卡即可跑完 M1 全部实验；多卡（双 5090 DDP）留给 M2 数据扩充后。

## 7. 训练执行流程（SOP）

```
① 环境就绪（docs/环境搭建.md，5090 版：PyTorch 2.7+ / CUDA 12.8+）
② 数据下载（SFT + Eval + Probe）+ 质量检查（§3.4）→ 登记 data/README.md
③ 冒烟：max_train_samples=512，1 个 logging step 验证链路（含 torch.compile 预热）
④ 正式训练：完整 config（L1），wandb 记录 run
⑤ checkpoint 确认：output_dir 下 adapter 完整（adapter_config.json + safetensors）
⑥ 评测：Probe 快速验证 → Eval 全量 + 分模块（§8）→ 登记 docs/实验记录.md
⑦ 上传 adapter 到 HF Hub / 网盘（不提交进 git）
```

- **中途失败**：TRL 自动保存 checkpoint，`bash scripts/train.sh <cfg> --resume` 续训（已实现）。
- **任何实验改动 = 一次 git 提交**（config/ 变更单独提交）。

## 8. 评测方案（5090 加速版）

### 8.1 指标

| 层级 | 指标 | 归属 |
|---|---|---|
| 官方评测集 | **Mining-Engineering-Eval（301 条）** 准确率/一致性 | 高校方实现 |
| 分模块 | 按 `source` 六模块分别计算指标（定位能力短板） | 高校方实现 |
| 外部基准 | **IndustryBench 中文子集**（阿里多语言工业知识基准，可选） | 高校方实现 |
| 工业 | **待企业方确认**（如 F1、分类准确率、抽取字段准确率、成本…） | 企业方定义口径 |

### 8.2 对照要求

- 同一评测集、同一 prompt 模板：基座（zero-shot） vs 微调后；CoT 实验单独对比。
- 评测代码与数据集版本随 PR 进仓库，保证可比。

### 8.3 记录

- 每个实验登记 `docs/实验记录.md`（表格 + wandb 链接），由企业方确认指标口径后归档。

### 8.4 5090 评测加速（M1 可选）

- **方案 A（默认）**：HF `generate` + `batch=8` + SDPA，301 条约 10~20 分钟，零额外依赖；
- **方案 B（提速）**：接入 **vLLM**（[5090 + WSL2 已验证可用](https://github.com/vllm-project/vllm/issues/37242)），生成提速 5~10 倍，分钟级完成；代价是多一个推理依赖。
- 建议 M1 先 A 后 B，B 作为 M2 常规评测底座。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **Blackwell 兼容性**（PyTorch <2.7 / FA2 / bitsandbytes） | 跑不起来或性能差 | 严格按 §6.1 环境清单；不用 FA2/QLoRA；Windows 原生不行就 WSL2 |
| 数据源单一（矿建领域） | 泛化局限 | 分模块定位短板；后续扩充其他工业数据（M2） |
| CoT 数据质量波动 | 学错推理模式 | 抽查 `<think>` 残片与事实错误；对比 L1/C1 实验决定 |
| 过拟合（5 千条规模） | 泛化差 | r=8、dropout、Eval/Probe 监控、epoch 上限 |
| 灾难性遗忘 | 通用能力退化 | 混入 5~10% 通用数据（后续阶段） |
| 效果不达预期 | 交付风险 | 数据迭代 > 超参 > r 值 > **升 14B LoRA**（5090 可跑） |
| 双方环境不一致 | 复现失败 | requirements.lock + 同版本 PyTorch/CUDA（**5090 与对方卡可能不同架构**，需约定统一软件栈） |
